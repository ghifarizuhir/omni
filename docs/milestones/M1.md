## Storage strategy

Most domain entities use a **document-style** column layout: structured fields are promoted only when they're filtered or indexed (`status`, `severity`, `priority`, `isMajor`, `tenantId`); the rest of the entity lives in a `data` JSON column. This kept M1 small without sacrificing the indexes that the UI's filter views need.

The `Tenant`/`User`/`Membership`/`Session` model is fully normalized — it gets used in M2 immediately, so the cost was worth paying up front.

## How to use

```bash
# First-time setup
cp .env.example .env.local
echo "DATABASE_URL=file:$PWD/prisma/dev.db" >> .env.local
npm run db:migrate    # runs prisma migrate dev
npm run db:seed       # populates from src/mocks/

# Iterate
npm run db:reset      # nuke + reseed
npm run server:watch  # API on :3001
npm test              # vitest run
```

## Rollback

The frontend still respects `VITE_API_MODE=mock`, which routes traffic through in-process mocks. Per-domain fallback isn't wired separately — flip the global flag.

## Known limitations

- SQLite for dev means no `String[]` (we use JSON), no `JSONB` operators, no concurrent writes at scale. Production uses Postgres.
- No pagination yet — list endpoints return whole arrays. Acceptable for current data volumes; add cursor-based pagination when a table grows past ~10k rows.
- Services / availability / capacity / platform routes still mock-backed in M1. Migrated in M3.
