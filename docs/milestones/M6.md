### Headline risks

1. **🚨 Tenant isolation gap (security-critical).** The session middleware does not throw on missing sessions in prod; it just leaves `req.session = undefined` and `req.tenantId = undefined`. No route except `/admin/*` and `POST /events/ingest` calls `requireAuth` or `requirePermission`. Repositories then call `prisma.findMany({ where: { tenantId: undefined } })`, which Prisma treats as **no filter at all** — an unauthenticated caller can read every tenant's CIs, incidents, events, etc. **Fix: mount `requireAuth` globally on the `/api/v1` router (except `/auth/login`) before M6 closes.** Tracked as M6.9.

2. **Endpoint authorization gap.** Per the service-endpoint matrix (`docs/audits/service-endpoint-matrix.md`): 61 / 68 endpoints (89.7%) lack `requirePermission(...)`. Even after M6.9 (auth gate), any authenticated user gets read access to every resource. Need per-resource permission keys.

3. **Frontend RBAC engine is mock-driven.** `CurrentUserContext` seeds React state from `src/mocks/rbac`; `requestResource` / `deploymentResource` import `mockCatalogItems` / `mockReleases` directly. The M2 backend RBAC tables (Role/Permission) are unused by the UI's row-level filtering. Note: the org tree (Division/Department/Team/Application/FunctionalRole) has **no server-side counterpart at all** — schema, repos, and routes are absent. Two options for M6.3:
   - (a) Port the org tree to Prisma + serve it under `/admin/org/*`.
   - (b) Move the static org data out of `mocks/` into `src/data/orgTree.ts` and treat it as build-time configuration; per-user placement still needs to come from the server (extend `/auth/me`).

   Recommend (b) for v1 — the org tree changes rarely; backend authorization is permission-based and already DB-backed.

4. **Write coverage gaps.** Matrix flags zero service methods for mutations in `incidents`, `cmdb`, `monitoring`, `availability`, `capacity` routes. Either the server routes exist and the frontend isn't calling them, or the writes are missing. M6.4 to confirm per page.

## M6.9 closeout (2026-05-14)

**Root cause.** `adminRouter.use(requirePermission('system.admin'))` had no path prefix. Because `adminRouter` is mounted alongside the other routers on the api root (no path prefix in `app.ts`), Express ran that middleware on **every** request that reached the api router. For admin users the middleware passed; for unauthenticated users it threw 401; for authenticated non-admin users it threw 403 on **every** route, including CMDB, incidents, etc.

That accidental behavior meant:
- Tests passed because the suite logs in as the admin user.
- The frontend works because `mockUsers[0]` is the admin.
- But every non-admin role on the server has been effectively locked out of the entire API since M2 — never noticed because no UI flow actually exercises a non-admin login against live data.
- And if you ever set `AUTH_REQUIRED=false`, the gate vanishes entirely, all routes pass `req.tenantId = 'tenant-demo'`, and cross-tenant queries return everything.

**Changes (one server, no client churn).**

| File | Change |
|------|--------|
| `server/routes/admin.ts` | `adminRouter.use('/admin', requirePermission('system.admin'))` — scope the system.admin guard to actual admin routes. |
| `server/app.ts` | Import `requireAuth` and mount `api.use(requireAuth)` between `authRouter` (public: login/logout/me) and the data routers. Now every data route is reached with `req.session` and `req.tenantId` set. |
| `server/__tests__/m6-auth-gate.test.ts` | Regression test: unauth → 401; non-admin → 403 on `/admin/*` but 200 on `/cis`; admin → 200 on both. |

**Verification.**

```
npm run lint   # clean
npm test       # 7 files, 93 tests pass (was 6/88; added 5 in m6-auth-gate)
```

**What this unblocks.**

- It is now safe to call non-admin permission checks per route (next M6 step — layer `requirePermission(...)` on data routes per `docs/audits/service-endpoint-matrix.md`).
- Non-admin users will now hit data endpoints from the UI. The frontend RBAC mock currently always seeds Sarah Chen (admin) so this didn't matter; once M6.3 wires the frontend to real `/auth/me`, operator/viewer roles will be reachable end-to-end.

**Known follow-ups carried into the matrix backlog.**

- `requirePermission('event.write')` on `POST /events/ingest` still fires `if (!req.session) → 401`. Inbound ingestion from external monitoring sources will need an API-key (HMAC-signed webhook) authenticator separate from cookie sessions. Out of scope for M6; tracked under M7 ingestion hardening.
- The other 60 unguarded routes still need permission keys layered on — the auth gate covers identity, not authorization. **(Resolved by M6.10.)**

## M6.4 closeout (2026-05-14)

**Deliverable:** [`docs/audits/mutation-audit.md`](../audits/mutation-audit.md) — 136 mutation handlers across 40 component files reviewed, with status per handler and a phased remediation roadmap.

**Headline metric.** Of 136 mutation handlers found across Incidents, Changes, CMDB, Monitoring, Requests, KB, Portal, and Admin RBAC pages:

| Status | Count | Meaning |
|--------|-------|---------|
| 🔴 Local-only (no server call) | 127 | Mutation evaporates on page reload |

| 🟡 Calls server, no refresh | 3 | UI drifts from server state |
| ✅ Fully wired (guarded + refreshed) | 0 | — |

**Most damaging finding.** This contradicts the **M3 backend-migration exit criterion** ("Every UI action that should mutate state has a matching write endpoint, validated server-side"). M3 shipped read endpoints for every domain, but the write surface is still:

| Domain | Write endpoints today |
|--------|------------------------|
| Auth | `POST /auth/login`, `POST /auth/logout` |
| Admin | `POST/PATCH/DELETE /admin/roles`, `PUT /admin/memberships/:id/roles` |
| Events | `POST /events/ingest` (webhook ingest, not user-driven) |
| Integrations | `POST/PATCH/DELETE /integrations` |
| **Everything else** | **None** |

Incidents, changes, CMDB, monitoring rules, alert routes, requests, KB, problems, releases, and deployments have **zero write routes**. UI Save/Approve/Close/Cancel buttons mutate React state only.

**Top 5 highest-impact fixes** (full list in audit doc §"Top 10 Priorities"):

1. `IncidentDetail.tsx:289` — `handleResolve` updates `setStatus('resolved')` only. The Resolve modal collects summary / rootCause / workaround but discards them. **Core ITSM workflow is non-functional.**
2. `NewChange.tsx:798-803` — "Submit for review" calls `localStorage.removeItem()` + `navigate()`, **never POSTs**. UI then navigates to a change ID that doesn't exist.
3. `RequestDetail.tsx:101-107` — Approve/Reject modals collect decisions and rationale; only local state is touched. Approval audit trail never recorded.
4. `AlertRouting.tsx:152-155` — Save button mutates in-memory `routes` array. Production alert escalation rules can't be edited.
5. `ChangeDetail.tsx:897` — Tech-assessment save is local-only; CAB approval gates UI but isn't enforced server-side.

**Why M3 looked "done."** The seed has only one tenant + one admin user. Tests always log in as the seed admin, so:
- The "fully gated by admin" accidental side-effect of `adminRouter.use(...)` (M6.9) was invisible.
- The lack of write endpoints was invisible: every `setState`-based mutation looked right on the screen during a single session.
- Without persistence checks across sessions or contract tests, the gap stays hidden.

**Action.** Closed M6.4. Opened **M6.11** to track the phased remediation. M6.11 is a multi-milestone effort (≈ 4–5 weeks per the audit roadmap), not a M6 sub-task — recommend treating it as its own milestone or interleaving with M7 work. Also flagging the M3 status in `BACKEND-MIGRATION-STRATEGY.md` since "M3 done" misrepresents the actual write coverage.

**The pattern for the rest of M6.11.** Each remaining write follows this shape:

1. Pick the existing permission key (or add to the catalog if the verb is genuinely new).
2. Add a repo function: validate → snapshot → transaction (update + side-effect rows) → return `{ before, after, internalId }`.
3. Add the route: Zod body → `requirePermission(...)` → call repo → emit audit log → respond with the updated snapshot.
4. Add a service method that mirrors the route signature.
5. Rewire the UI handler: optimistic local update → service call → `refresh()` from `useResource`.
6. Write a test covering: unauth, body validation, 404, happy path, GET round-trip, side-effects (timeline / audit log), and 403 for missing permission.

Total turnaround for the incident-resolve slice: ~150 lines of code + 130 lines of test, ~30 minutes. The remaining ~50 endpoints in the audit roadmap can be parallelized once the pattern is locked in.

## M6.6 — Session-expiry UX (2026-05-14)

**Pattern.** A custom DOM event `auth:session-expired` decouples the producer (`apiFetch`) from the consumer (router-level navigator). No module coupling across `services/` ↔ `lib/auth/` ↔ `routes/`.

| File | Change |
|------|--------|
| `src/services/core.ts` | On any 401 response, `window.dispatchEvent(new CustomEvent('auth:session-expired', { detail: { from } }))` before throwing `ApiError`. |
| `src/lib/auth/session.ts` | Window listener flushes the cached `AuthSession` so `useAuthSession()` consumers immediately re-render anonymous. |
| `src/components/layout/AppShell.tsx` | `useEffect` listener: when fired, `navigate('/login', { replace: true, state: { from, reason: 'expired' } })`. Skips when already on `/login` to avoid loops. |
| `src/routes/Login.tsx` | Reads `location.state.reason === 'expired'` and renders an amber banner ("Your session expired. Please sign in again to pick up where you left off."). The existing `from` redirect-back path is preserved. |

**Note on form state.** The current implementation does *not* serialize in-flight form state across the redirect (the strategy doc mentioned "where feasible"). Form drafts that should survive a session expiry need to opt in by writing to `localStorage` themselves — Login's `from` path then brings the user back to the originating route to recover. Recommending we tackle this incrementally per page in M6.11.

## M6.7 — Shared Zod schemas (2026-05-14)

**Pattern.** `src/shared/schemas/<domain>.ts` exports both the Zod schema and a derived `z.infer<>` type. Both server routes and client services / forms import from there.

| File | Role |
|------|------|
| `src/shared/schemas/incident.ts` | Hosts `resolveIncidentSchema`, `addIncidentCommentSchema`, `setIncidentStatusSchema` (+ inferred types). |
| `server/routes/incidents.ts` | Drops its local Zod definitions, imports from `../../src/shared/schemas/incident`. The server tsconfig already includes `../src/types/**`; widened to pick up `../src/shared/**`. |
| `src/services/incidentsService.ts` | Re-exports the schemas + types for client callers who want client-side validation without learning the `shared/schemas/` path. |

**Why this is enough for v1.** Drift between client and server only matters when both sides define the schema. With one source of truth, schema changes show up as TS compile errors on both sides simultaneously. Adding the same pattern to changes, requests, and the rest of M6.11 is a mechanical follow-up — pull the `z.object(...)` out of `server/routes/itsm.ts`, drop in `src/shared/schemas/<domain>.ts`, re-import.

**Bonus.** While migrating the incident-resolve test to use the shared schema, the suite revealed a non-hermetic bug: `incidents-resolve.test.ts` was picking an open incident from the seed and resolving it, so a second run found nothing to resolve. Fixed by **cloning the fixture row** in `beforeAll` (`{publicId}-RESOLVE-{rand}`). Suite is now stable across re-runs (verified twice in a row).

## M6.8 — Contract tests (2026-05-14)

**Pattern.** A single `server/__tests__/contract.test.ts` defines a minimum-shape Zod schema per domain (`.passthrough()` to ignore extra server fields) and validates the GET responses against it. A drift between server snapshot and TS type now fails CI rather than appearing as a runtime crash in production.

**Coverage** (12 endpoints):

- List: `/cis`, `/incidents`, `/events`, `/monitoring/rules`, `/changes`, `/requests`, `/releases`, `/deployments`, `/problems`, `/kb/articles`, `/integrations`.
- Singleton: `/auth/me`.

Each schema pins down the must-have fields (`id`, `publicId`, the most-queried discriminators like `status`/`type`) plus structural assumptions (e.g. `request.workflow.steps[]` has `id` and `status`). Adding more is one-line: a new `schema` constant + an `expectListShape(path, schema)` call.

**Why this is the right minimum.** The audit had flagged that "tests always log in as admin and never exercise the round-trip shape", and the M6.4 work showed the consequences (writes silently 200'ing without persisting). Contract tests catch the inverse: reads silently changing shape. The two together close the audit loop.
